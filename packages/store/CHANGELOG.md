# @jimhoyd/urlcode-store

## Unreleased

The host lease (core's `joinHostLease`) never compares two hosts' clocks (#978): each renewal writes a larger `heartbeat_at`, and a process judges another host's row by whether it advances, timed on its own monotonic clock. A joiner watches another host's row for up to 20 s, refusing if it advances and deleting it if it stays silent, so a joiner whose clock runs ahead no longer evicts a live holder and a crashed host whose clock ran ahead blocks a restart for 20 s, not for the skew. Every heartbeat re-checks the table: a process that finds another host's row loses the lease, deletes its own row, logs it, does not re-insert it, and rejoins by itself once no other host holds one. A failed heartbeat is logged. Every store write checks the lease first, inside its own transaction under the write lock: while the lease is lost, or not renewed for 10 s and its row cannot be confirmed, the write answers `503 storage_unavailable` and writes nothing. Reads keep working. `StoreDatabase.transaction` takes a third `guarded` argument and a `writeGuard`.

**Sorted and filtered lists in SQL (#951).** A sorted or filtered page is now one counted keyset query through an index per `sortable` and `filterable` property, instead of reading every record in scope and ordering it in memory. The indexes are derived from the declaration, built at activation in one write transaction before the declaration is recorded, and dropped (with stale interval indexes) once no live activation declares them. A string's index key maps UTF-8 lead bytes EE and EF above the four-byte ones, so SQLite's byte order is the documented UTF-16 code unit order; numbers, integers and booleans key as doubles. Results, `total`, cursors and `next` are unchanged, proved against the in-memory path on random data (non-ASCII, surrogate pairs, NUL, ties, absent values, every scope, deleted cursor records). While a collection holds a value the key cannot order exactly (a lone surrogate, or a type other than the declared one), found through one more normally empty index, its lists use the in-memory path. At 10,000 records a `sort=title` page went from 11.2 to 0.63 ms at p50, and 16 concurrent ones from 169 to 7.7 ms (89 to 1,887 lists/s) in one local run; a create with four list indexes cost 0.03 to 0.04 ms more. `npm run bench:store -- --lists` runs only the list parts.

**Edit and delete states, and values unique across owners (#952, #953).** *States:* a collection may declare `editable` and `deletable`, each in the shape of a transition's `from` with a value or a list of values per property (`editable: {status: draft}`, `deletable: {status: [draft, rejected]}`). Outside `editable` a `PUT` or `PATCH` answers `409 record_locked`, and outside `deletable` a `DELETE` does, writing nothing; the check reads the record inside the write's `BEGIN IMMEDIATE` transaction after the scope and `If-Match`, on HTTP, `StoreExports.update` and a host transaction's `update` and `remove`. Creates, transitions, increments, transfers and `ownerless-delete` are unaffected, so a request is still created with its `title` and `amount` and an approved one keeps the values its reviewer saw. Activation requires each named property to be in `readOnlyProperties` and each value to satisfy its schema, and refuses both on a membership or `readOnly` collection. On such a collection a record's `GET`/`HEAD` and `PUT`/`PATCH` answers carry `Allow` with the methods it takes now, and a collection-mount list carries `allow: {<id>: [methods]}`. *Unique:* `unique: [<property>, ...]` (at most 4; strings with `maxLength` at most 128, no default, not readOnly, not the key and not set or stamped by a transition) keeps each value unique across the whole collection, across owners on an owned collection, where `key` stays refused: a create, `PUT` or `PATCH` that would duplicate one answers `409 value_taken` with one issue naming the property (never the value or the holder), checked under the write lock through a partial expression index (`store_unique_*`, built on activation and dropped when no live declaration names it). Activation refuses stored duplicates. The refusal tells a caller that a value is in use, so it is for public handles (SECURITY.md). The OpenAPI description adds `record_locked` (naming the states), `value_taken`, the `Allow` header and the list's `allow`. `StateSpec` is exported. Each declaration changes the collection's fingerprint (#927).

**Breaking: named readers mounts (#944), and a step grid with an origin (#945).** *Readers:* `readers` is a map of named mounts, `readers: {<name>: {mount, members?, showOwner?, properties?}}` (at most 8), so one collection can serve a projected directory to every signed-in principal and a members-gated whole-record view (with `_owner`) to a few, for example `readers: {directory: {mount: /api/directory, properties: [name]}, audit: {mount: /api/audit, members: treasurers, showOwner: true}}`. Each mount keeps its own gate, projection, sort and filter rules, `may` and `ETag`, and a mount with neither `members` nor `properties` is still refused. The single-object form is gone: write `readers: {review: {mount: /api/review, members: reviewers}}` for the old `readers: {mount: /api/review, members: reviewers}`. Activation refuses two readers sharing a mount and names the mount in every readers diagnostic (`readers audit: ...`). OpenAPI describes each readers mount as its own path, and a projected or `showOwner` mount gets its own `Store<Collection><Name>ReaderRecord` and `...ReaderList` (`StoreNotesReaderRecord` becomes, for example, `StoreNotesReviewReaderRecord`). The declaration fingerprint covers every mount by name, and the normalized declaration now always carries `readers` (empty when none), so every collection's fingerprint changes once: as with any declaration change, the first activation of this release wins the declaration fence (#927). *Intervals:* `intervals.origin` (with `step` only) is where the grid counts from: an RFC 3339 date-time with `Z` or a fixed offset for date-time bounds (`origin: 1970-01-01T00:00:00+05:30` puts `step: PT1H` on the local hour at UTC+05:30, and `P1D` on local midnight there), or an integer for integer bounds; the default stays the epoch, or 0. The check compares residues modulo the step, so it is exact for any safe integer, and a `422` names the declared origin. It is a fixed offset, not a time zone: no daylight saving is followed (see docs/STORE.md, "A grid with an origin").

The network filesystem check and the `store_servers` lease now run through core's shared helpers (`refuseNetworkFilesystem`, `joinHostLease` in `@jimhoyd/urlcode/extensions`, #941), which auth and audit use for their own databases. The store's behavior, table and messages are unchanged.

**Hermetic test runs and a membership seed (#930).** In a hermetic run (`urlcode test`, `audit`, `benchmark`; `HostContext.hermetic`) the host ignores `database` and `STORE_DATABASE` and opens a fresh database in the run's data directory. The registration then accepts a test seed (`storeSeedSchema`, exported): `tests/seed.json` `{"store": {"members": {"<membership collection>": ["<principal id>", ...]}}}` adds each member before the first fixture, as `urlcode-store members add` does (actor `operator`, audited on an `audit: true` collection); a name that is not a membership collection refuses activation.

**Slot length and grid, members-gated create, and projected readers (#929).** *Intervals:* `intervals.length` fixes every interval's length and `intervals.step` puts both bounds on a grid: an ISO 8601 duration of whole days, hours, minutes and seconds (`PT1H`, `PT30M`, `P1D`) for date-time bounds, counted from 1970-01-01T00:00:00Z (so `step: PT1H` is on the hour, UTC), or a positive integer for `integer` bounds (a `number` bound takes neither). A create, `PUT`, `PATCH`, transition or host transaction leaving an end that is not exactly `start + length`, or a bound off the grid, is `422 invalid_record` with keyword `intervals` and a message naming the declaration, never the value; activation refuses a `length` that is not a multiple of `step`, and stored records that break either. *Create:* `create: {members: <membership collection>}` admits only that list's principals to create, on `POST <mount>`, `StoreExports` and a host transaction: `401 principal_required` without a principal (a shared collection included), and `403 membership_required` as the first statement of the write transaction, before the body, the retained `Idempotency-Key` or any record is read, so a removed member's retry is refused rather than replayed. Not on a membership collection or a `readOnly` one. *Readers:* `readers.properties: [<property>, ...]` makes the readers mount a projection: each record is answered as `id`, the listed properties and (with `showOwner`) `_owner`, never `createdAt`, `updatedAt` or another property; sort and filters take only listed properties (`400 invalid_query` for any other, even one the collection declares sortable or filterable); `may` lists only transitions whose `from` names only listed properties; and the `ETag` and `etags` are the SHA-256 of the projection, so they change only when a shown property does (a transfer moving a hidden balance does not change them) and are not the record's own `ETag`. With `properties`, `readers.members` is optional: without it every principal the mount's route admits reads the projection, which is the transfer directory (`readers: {mount: /api/directory, properties: [name]}` finds a recipient's wallet id by name without disclosing any balance). A readers declaration with neither `members` nor `properties` is refused. `CreateSpec` is exported. The OpenAPI description lists the `401`/`403` of a gated create, the length and step in the `422`, and a projected `Store<Collection>ReaderRecord` with only the listed properties and the projection's sorts and filters. Each declaration changes the collection's fingerprint (#927).

**The transfers authoring surface names the issuer pattern (#932).** Its description says the amount defaults to 0, is in `readOnlyProperties` and is set by no transition, and that value comes in through an issuer: a transfer with a negative `min` and `members: <membership collection>`. Its goals add `issuer`, `issuers` and `mint`, so `urlcode plan-feature` finds it for a minting goal. Core's new `store-booking` and `store-credits` recipes run here, through the CLI's `validate`, `test` and `audit` with `--local-review`, against this extension (test/recipes.test.ts).

**Installed guidance points at installed pages (#931).** `urlcode extensions add store` no longer names `docs/STORE.md`, which a site does not have: its notes and the `STORE_DURABILITY` description point at the installed README, `node_modules/@jimhoyd/urlcode-store/README.md`, and at `urlcode docs search`. Transfers and intervals have their own README headings instead of sharing "Transitions", so `urlcode docs search "intervals"` (or `"transfers"`) lands on its section.

**Breaking: several serving processes on one host (#927).** The supported topology is N serving processes or containers on one host, on one release, with the database on local disk. Schema version 5 adds `store_declarations`, `store_servers` and the drain lease; opening a version 4 database upgrades it forward in one transaction, keeping when the drain last kept up. *Declaration fence:* each activation records every collection's declaration fingerprint (SHA-256 of the canonical normalized declaration) and the schema version, replacing what any earlier activation recorded; every write transaction (HTTP writes, increments, transitions, transfers, short-link clicks, `StoreExports` writes, and each collection a host `transaction()` writes) first compares its own with them and with the file's `user_version` under the write lock, and on a difference answers `503 storage_unavailable` (`The collection was redeclared by another process`) and writes nothing. Reads are not fenced. In a dev reload the replacement's declaration wins, so the retiring runtime's writes to a changed collection are refused (before, they could write rows the new declaration could not represent); a reload that fails after the store activated records the serving declaration again. The `urlcode-store` commands that write are refused while a live server has recorded a different declaration of a collection they touch. *Refused setups:* opening the database refuses a directory on a network filesystem by its Linux `statfs` type (NFS, SMB, SMB2, CIFS, FUSE, 9P, Ceph, AFS; not checked on macOS or Windows), and a serving process joins a lease table (instance, hostname, Linux boot id, pid; heartbeat every 5 s, live 20 s) and refuses to activate while a live peer runs on another host (another boot id, or another hostname when either has no boot id); an activation that finds a live peer logs one `extension_warning` that throttle policies and origin caches are per process. *One audit drainer:* the drain marker carries a lease (`holder`, `lease_until`, 10 s); only its holder peeks and acks, and a peer takes over once it expires or its holder closes. `createStore` takes a `probe` test seam; operators never set it. A previous release (schema version 4) running beside this one is not fenced.

**Transfers keep the sum on every write (#928).** On a collection declaring `transfers`, deleting a record whose amount property is nonzero is refused with `409 balance_not_zero` (a fixed message naming no amount) and nothing is written, on every delete path: `DELETE <mount>/<id>`, a host transaction's `remove` and `urlcode-store ownerless-delete` (the records export has no delete), which refuses as a whole when any ownerless record holds a balance. A zero-balance record is deleted as before. Activation now also requires the amount property to be listed in `readOnlyProperties` (so no create, `PUT` or `PATCH` body sets it and `PUT` keeps it), to default to `0` (so a create adds nothing) and not to be set or stamped by a transition. The OpenAPI description lists the `409` on `DELETE` for such collections. Breaking for a collection that opened records with a nonzero default: fund them with a transfer from a members-gated issuer.

**Declared transfers (#902).** A collection may declare `transfers: {<name>: {amount, min?, members?}}`: `POST <mount>/transfers/<name>` with the JSON body `{from, to, amount}` (two distinct record ids and a positive whole number at most 2^53 - 1, validated by a generated schema; anything else, a fraction included, is `422 invalid_transfer` with the body-validation issues) subtracts `amount` from the `from` record's `amount` property and adds it to the `to` record's in one `BEGIN IMMEDIATE` transaction, with both new `updatedAt`s, both audit events and the `Idempotency-Key` claim, so the sum over the collection never changes. A debit below `min` (default 0) is `409 insufficient_balance`; a value outside the property's schema or the safe integers is `409 transfer_limit` (no issue list, so it never describes another owner's balance); a stored record without a whole balance is `409 transfer_conflict`; every refusal writes nothing. The amount property must be a required `integer` in `readOnlyProperties` with default 0 (#928), and not an increment, an `intervals` property or set by a transition; a `readOnlyProperties` entry a transfer moves no longer needs a transition. Authorization: on an owned collection the caller debits only a record it owns (another owner's is the `404` of a missing id) and may credit any owned record; on a shared collection anyone who reaches the mount may move between any two records; `members` admits only a membership collection's members (`403` before any record is read), and with a negative `min` makes an issuer whose negative balance is the supply outstanding. The floor is checked before the credited record is read, so an id cannot be probed without funds to move. The answer is `200 {from, to?}` with `from`'s `ETag`; `to` only when the caller may read it. `If-Match` applies to `from`, and a replayed key answers both records as they are now. Audited collections record `store.record.transferred` for each record with `{collection, transfer, side, counterpart, fields}`. `StoreRecords.transfer` and `StoreTransactionRecords.transfer` run it for trusted code; `TransferSpec`, `Transferred`, `StoreTransferRequest` and `StoreTransferResult` are exported. The OpenAPI description adds `POST <mount>/transfers/<name>` with `Store<Collection>Transfer` and `Store<Collection>Transferred`. Conservation is tested with 200 interleaved transfers in one process and across four connections, and audit atomicity with a trigger-injected failure on the credited record.

**Declared non-overlapping intervals (#902).** A collection may declare `intervals: {start, end, within?, scope?, when?}`: among the records holding every `when` value, no two in the same scope with equal `within` values may hold overlapping half-open `[start, end)` intervals (adjacent ones are allowed). Every create, `PUT`, `PATCH` and transition is checked inside its own write transaction and refused with `409 interval_conflict`, writing nothing (a refused move keeps its slot; a transition back into `when` is checked too). `scope: collection` (the default) constrains every record across owners on an owned collection, and `scope: owner` each owner's records alone. The body's `error.conflict.id` names the conflicting record only when the caller may read it (any record of a shared collection, only the caller's own on an owned one), so another owner's booking blocks without being disclosed. Bounds are required, both `integer`/`number` or both `format: date-time` strings, which must be UTC (`Z`) with at most millisecond precision (anything else, and an end not after its start, is `422 invalid_record` with keyword `intervals`) and compare as instants. The check reads one step of a partial expression index the declaration builds (activation creates it, and drops interval indexes no live activation declares): 2.4 µs at the median over 10,000 records, against 3.2 ms for the same query without the index (`npm run bench:store -- --intervals`, which this adds). Activation refuses stored records that overlap or break the rules, naming both ids, and `reassign` and `ownerless-assign` refuse a move that would give a principal overlapping intervals under `scope: owner`. The OpenAPI description lists `interval_conflict` and the `conflict` member of `StoreError`.

**Retry-safe host transactions (#902).** `StoreExports.transaction(work, {idempotencyKey, fingerprint?})` keeps the SHA-256 of the key and of the fingerprint with `work`'s return value (JSON that round-trips exactly, or `undefined`; at most 16 KiB) in the same transaction, and returns a copy of that value to a later call with the key and the same fingerprint without running `work` or writing anything; a different fingerprint is `422 idempotency_key_reused`. Racing calls with one key run `work` once, across connections too; a transaction that throws keeps nothing. The newest 1000 keys are kept, store-wide, and survive a restart. Schema version 4 adds the `store_transaction_results` table (the upgrade adds it and changes nothing else). `TRANSACTION_RETRIES`, `StoreTransactionOptions`, `StoreTransaction`, `StoreTransactionRecords`, `IntervalSpec` and `IntervalScope` are exported.

**Breaking: named record schemas, and defaults and read-only properties on the collection (#908).** A collection's `schema` may name one of the project's named schemas (top-level `schemas:`, `ExtensionActivation.schemas`) instead of writing one inline, so one schema is a collection's record shape, a route's request body and an MCP tool's arguments, and all three refuse the same invalid input at the same pointer with the same issue. The named schema must satisfy the inline restrictions (a flat object of scalar properties, `additionalProperties: false`, no `$defs`); activation refuses one that does not, naming the collection, the schema and the pointer, and an unknown name. **Breaking:** a record schema, inline or named, is value shape only: `default` and `readOnly` on a property are refused at activation, and the collection carries them instead as `defaults: {<property>: <value>}` and `readOnlyProperties: [<property>]`, with the same behavior as before (a default must satisfy its property's schema; a read-only property changes only through a transition). `StoreRecords` adds `defaults` and `readOnlyProperties`; `PropertySchema` loses `default`/`readOnly`; `CollectionSpec.schema` is `RecordSchema | string`; `normalize`, `compileRecordSchema` and the `Collection` constructor take the project's named schemas; `OwnerlessOptions`, `ReassignOptions` and `MembershipOptions` take `schemas` (the CLI passes the project's). The OpenAPI description references a named schema's component (`#/components/schemas/<name>/properties/<property>`, with the collection's `default`/`readOnly` beside it) instead of copying it, and `Store<Collection>Create` is the component itself when the collection takes it unchanged as a create body.

**Commit durability is an operator setting (#859).** `store({durability: 'full' | 'normal'})` in `host.mjs`, else `STORE_DURABILITY`, else `full`, sets the connection's SQLite `synchronous` level: `full` (the default and the previous behavior) fsyncs every commit; `normal` fsyncs only at checkpoints, so commits are faster and the last ones before a power loss or OS crash can be lost (a process crash loses nothing; the database never corrupts). Any other value, `off` and `extra` included, is refused by `host()` before anything is served. An activation with `normal` writes one `extension_warning` to the operator log. The `urlcode-store` operator commands always commit with `full`. `StoreExtensionOptions.durability`, `STORE_DURABILITIES` and the `StoreDurability` type are exported, and `createStore` returns the resolved `durability`. docs/STORE.md "Durability" documents the trade-off with the docs/CAPACITY.md measurements.

**Breaking: record schemas are JSON Schema 2020-12 (#861, #881).** A collection declares `schema:`, a JSON Schema 2020-12 object schema in core's request body profile (the same keyword allowlist, formats, regex admission, limits and Ajv options as `request.body.<METHOD>.schema`), instead of `fields:`. The root is `type: object` with `properties` (1 to 64), optional `required`, `$schema`, `title`, `description` and `$comment`, and `additionalProperties: false` written out; each property has one scalar `type` and any other profile keyword. The store acts on two standard annotations on a property: `default` (stored on create and on `PUT`) and `readOnly: true`, which replaces `transitionOnly` (only a transition changes it; a required readOnly property needs a default). `format: http-url` is gone: a short link's destination is a required `format: uri` property, and every write to it also takes only an absolute HTTP(S) URL without credentials or whitespace. A record that breaks the schema, a readOnly property in a body, a cleared increment and a membership key that is not a principal id are `422 invalid_record` with `issues` in core's body-validation issue shape (was `400` with `fields`); the validator reports the first failure. A write is judged as the record it leaves, so `PATCH` clearing a required property is the `required` issue, and `required` with a `default` is now allowed. Stored rows are judged without `required`, so adding a required property does not stop a populated collection; such a record's next write must supply it. List filters are judged by the property's schema through the same validator (`must be one of the declared values`, `does not match the declared pattern`, ...). `checkValue`, `FieldSpec` and `FieldType` are removed; `compileRecordSchema`, `RecordSchema`, `PropertySchema` and `PropertyType` are exported, `NormalizedSpec.fields` is `records` (the compiled schema), `StoreError` takes `{fields?, issues?}` details, `StoreRecords.fields` is `schema` (a deep-frozen copy) and `LIMITS.fields`/`stringLength` are `LIMITS.properties`. Records stored as JSON rows are unchanged; no database migration.

**OpenAPI description (#881).** The registration implements core's `describe()`, so `urlcode openapi --host-file` lists every collection, readers, `by: others` transition and short-link mount as real paths: list (limit, cursor, sort, filters with the property schemas), create, read, replace, patch, delete, increment and transitions, with `If-Match`, `Idempotency-Key`, `ETag`, `Allow-Transitions`, `Location` and `Idempotency-Replayed`, and `Store<Collection>Record`/`Create`/`Patch`/`List` schemas built from the record schema.

**Audit delivery status for operator commands (#875).** A `urlcode-store` command that records audit events (`members add|remove`, `reassign`, `ownerless-assign`, `ownerless-delete` on an `audit: true` collection; not a dry run) adds `undeliveredEvents` (events waiting per audited collection it touched), `lastAuditDrain` (ISO time the serving process's drain last acked events or found the outbox empty, `null` if never) and, when events wait and no drain has kept up in the last 60 seconds, a `warning` to its JSON report; the library functions return the same fields. Schema version 3 adds the one-row `store_audit_drain` table, which the store's audit producer updates at most every 10 seconds; opening a version 2 database upgrades it forward in one transaction.

**Breaking: store screens removed (#883).** The `screens` configuration, `contributes.ui.screens`, `storeScreens`, `contributedScreens`, `screensSchema` and the `StoreScreen` type are gone, and so is the optional `@jimhoyd/urlcode-ui` peer dependency (the ui extension was deleted). `--example` writes the `/api/todos` JSON mount only, never a `/todos` screen. The HTTP contract is unchanged: transitions, readers, `etags`, `may` and `Allow-Transitions` are what an application's own frontend reads, as `proofs/private-requests/client` does.

**Operator gaps (#875).** On an owned collection declaring `audit: true`, `urlcode-store reassign` records every moved record as `store.record.reassigned` (subject `<collection>/<id>`, metadata `{collection, from, to}`), and `ownerless-assign` and `ownerless-delete` record `store.record.reassigned` (`{collection, to}`) or `store.record.deleted` (`{collection, ownerless: true}`), all in the same transaction as the change. Each command counts its events first and refuses whole with `503 audit_backlog`, before writing and on a dry run too, when they would take a collection past its 1000 undelivered events. The reassign report adds `auditEvents`. Every writing command (`members add|remove`, `reassign`, `ownerless-assign`, `ownerless-delete`) takes `--actor <principal id>` (library: `actor`), the events' actor, default `operator`; it is validated like a principal id and is operator-asserted, not authenticated. **Breaking:** `ownerless-assign` and `ownerless-delete` need `--project` and a collection declared `ownership: owner`, and `assignOwnerless`/`deleteOwnerless` take `(database, {collections, collection, owner?, actor?})`. **Breaking:** a list filter value outside the field's `minimum`/`maximum`, `minLength`/`maxLength` or `format` is `400 invalid_query` with the write path's fixed message (the value is never echoed), on owner and readers mounts, instead of an empty page.

**What the caller may run (#873).** **Breaking:** every list answer (collection mount and readers mount) adds `may: {<id>: [transition names]}`, the declared transitions the caller may run on each listed record now, and a single-record answer (`GET`/`HEAD`, a readers mount's `GET <mount>/<id>`, and the answer to a create, `PUT`, `PATCH`, increment or transition) adds the same list as the `Allow-Transitions` header (names separated by `, `, empty when none). It is computed in the answer's own transaction from what the transition checks: the record's values against `from`, its owner against `by` (a `by: others` transition is never offered on the caller's own record), and the caller's own membership for a `members` gate, looked up at most once per distinct gate and only when a listed record could take it, never per record. It never names a gate or another principal; a caller with no principal is offered only ungated transitions of a shared collection, and a `readOnly` collection none. An empty list is now `{"items":[],"total":0,"may":{},"etags":{}}`. `Collection.list` and the write methods take an optional trailing `Viewer` (`{principal}`); `Collection.show` returns `{record, may}`, `getAcross` now returns `{record, may}`, and the types `Page`, `Shown` and `Viewer` are exported. `StoreExports` is unchanged.

**Membership follow-ups (#866).** `urlcode-store members add|remove|list --database <file> --project <app> --collection <name> [--principal <id>]` wires `addMember`, `removeMember` and `listMembers` into the CLI: it reads the declared collections through core's loader, validates the principal id without echoing a refused one, prints JSON and may run while the server serves. A membership collection may now declare `audit: true` (before, activation refused it): every added or removed member, from the CLI, the library functions, `StoreExports` or `reassign`, is recorded as `store.membership.added`/`store.membership.removed` (subject `<collection>/<principal id>`, metadata `{collection}`, actor `operator` for the operator path) in the same transaction as the member row, and refused with `503 audit_backlog` at the cap; the operator path validates the event with audit's own validator and needs the audit package installed. **Breaking:** an update that changes a membership collection's key is `400` (remove the member and add the new one). `reassign` also moves `--from`'s membership in every membership collection (or the one `--collection` names) in the same transaction as the record moves: the entry becomes `--to`'s, or is removed when `--to` already is a member; its report gains `memberships: [{collection, toWasMember}]` and `--collection` accepts a membership collection. **Breaking:** a list filter value outside the field's `enum` is `400 invalid_query` (`is not one of the allowed values`) instead of an empty page, on owner and readers mounts alike. `readers.showOwner: true` adds each record's owner principal id as `_owner` to the readers mount's answers only; it is off by default. `ReassignMembershipReport` is exported.

**Screens over transitions (#863).** A screen over a collection with `transitionOnly` fields is no longer refused: the store contributes the collection's transitions and `idempotency` to ui, which shows those fields read-only and each transition as a button. A screen may declare `readers: true` to list the collection's readers mount instead, read-only, offering exactly the `by: others` transitions on their own mounts; the default screen offers the transitions served on the collection mount. `readers: true` on a collection without `readers` refuses activation, and a `readOnly` collection's screen offers no transitions. **Breaking:** every list answer (collection mount and readers mount) adds `etags`, each listed record's current `ETag` keyed by id, so a client can send `If-Match` for the version it listed; an empty list is `{"items":[],"total":0,"etags":{}}`.

`urlcode-store backup --database <file> --destination <file>` takes an online backup (#859): a consistent copy through `node:sqlite`'s `backup()` (Node 22.16 or newer) while the server keeps serving. Both paths are absolute; it refuses a source that is not a private store database of a schema this release understands and an existing destination, writes the copy `0600` in a private temporary directory beside the destination, checks its `application_id`, `user_version` and `integrity_check`, links it into place and prints `{format, schemaVersion, bytes, destination}`. Exported as `backupStore`.

The definition declares its deployment targets (node), which `npm run build:addons` writes into `urlcode.json` as `targets` (#859); core refuses a registration whose targets differ, and the capability preflight refuses a recipe or plan that uses this extension on any other target.

**Membership gates and cross-owner reads (#863).** A collection may declare `membership: true` with a `key`: one record per member, keyed by principal id (a key value that is not a principal id is `400`). It has no mount and no HTTP API, and activation refuses it with `mount`, `ownership`, `transitions`, `readers`, `increments`, `idempotency`, `sortable`, `filterable`, `readOnly` or `audit`, and refuses a screen over it; `mount` is now required only on other collections. The operator maintains it with the new `addMember`, `removeMember` and `listMembers` exports (one transaction each, safe while serving; `addMember` creates the database when absent), and trusted extension code through `StoreExports`. A transition may declare `members: <membership collection>`: after the principal (`401`), a non-member gets `403 membership_required`, checked first inside the write transaction, before the retained `Idempotency-Key` and before any record is read, so the answer is the same for an existing and a missing id and a removed member's retry is refused; host transactions pass the same gate. An owned collection may declare `readers: {mount, members}`: members list (with the collection's `limit`, `cursor`, `sort` and filters) and read every owner's records, read-only, at `GET <mount>` and `GET <mount>/<id>` on a separate principal-guarded route; records with no owner are left out and the stored owner is never shown. Activation refuses `members` naming an undeclared or non-membership collection and `readers` on a shared collection or a conflicting mount. The #843 proof now runs on the store and auth alone, with no application code.

**Breaking: result-aware retries, declared transitions and host transactions (#835, second slice).** A retained `Idempotency-Key` no longer answers `409 idempotency_duplicate`: a retry with the same request (method, path and canonical JSON body, hashed) replays the first answer's status with the record as it is now, its current `ETag` and `Idempotency-Replayed: true` (a record since deleted or moved out of the caller's scope is `404`), and the same key on a different request is `422 idempotency_key_reused`; neither writes anything, and of racing requests with one key exactly one runs. A key is now scoped to the request principal when there is one, else to the network client (before: the network client, plus the principal on an owned collection). Schema version 2 replaces `store_idempotency` with a table that keeps the fingerprint, status and record id (never record values) and drops version 1 claims, which cannot be replayed. Collections may declare `transitions.<name>: {from, set, stamp?, by?, mount?}`, served at `POST <mount>/<id>/<name>` (or, for `by: others` on an owned collection, `POST <transition mount>/<id>`, a separate principal-guarded route): the record must hold every `from` value (`409 transition_conflict` otherwise), the owner of a `by: others` record gets `403 own_record_refused`, and `If-Match`, `Idempotency-Key`, `readOnly` and audit (`store.record.transitioned` with the transition name) apply. A field may declare `transitionOnly: true`: bodies cannot set it and `PUT` keeps it; a screen over such a collection is refused. `StoreExports` gains `records(name).transition(...)` and `transaction(work)`, which runs synchronous `create`/`get`/`update`/`remove`/`transition`/`list` calls across collections as one `BEGIN IMMEDIATE` transaction (trusted host code; a returned promise is refused and rolled back). Collection write methods now take a `Retry` (`{key, fingerprint}`) instead of a key string and return `Written` (`{status, record, replayed}`); `validateIdempotency` is replaced by `idempotencyConfig`.

**Breaking: SQLite engine (#835, first slice).** The JSON-file engine is gone: every collection's records, retained `Idempotency-Key` claims and undelivered audit events are rows of one SQLite database per site (`node:sqlite`; `store({ database })`, else `STORE_DATABASE`, else `data/store.sqlite` beside `host.mjs`, outside `app/`, created `0600` in a `0700` directory). The `directory` option, `STORE_DIRECTORY`, the per-collection `<name>.json` files, the `.store.lock` file and `lockStoreDirectory` are removed, and old JSON data files are neither read nor imported. The schema is initialized forward only (`PRAGMA application_id` and `user_version`; an up-to-date database is left unchanged, a newer or foreign file refuses activation). Every write is one `BEGIN IMMEDIATE` transaction that commits the record, its unique key, its `Idempotency-Key` claim and its audit event together or rolls all of them back; `If-Match`, quotas, key uniqueness and the audit backlog are checked inside it. Nothing is cached in memory: reads query the database, and a sorted or filtered list reads only the named fields before fetching its page. `updatedAt` now advances by at least one millisecond on every write, so two writes in the same millisecond get different ETags and exactly one of several concurrent writers holding the same `If-Match` wins (before, same-millisecond writes could share an ETag). A write blocked by another process's lock for 2 seconds answers `503 storage_unavailable`. One serving process per database is the supported deployment; a second is no longer refused (SQLite serializes it) and is not supported. The `urlcode-store` commands take `--database <file>` instead of `--directory`, never create a database, run as one transaction and may run while the server serves; `reassign` now moves every affected collection or none. A hot reload's activations share the registration's one connection, so the store no longer implements the core reload hand-off (`Collection.open(db)`/`close()` replace `open(files)`/`detach()`; `CollectionFile` is removed; `STORE_APPLICATION_ID` and `STORE_SCHEMA_VERSION` are exported). The store refuses a SQLite older than 3.44.6, 3.50.7 or 3.51.3, like audit and abuse.

Audited writes. A collection may declare `audit: true`: every create, replace, update, delete and increment is recorded as `store.record.created|replaced|updated|deleted|incremented` (subject `<collection>/<id>`, actor the request principal or `anonymous`, metadata `{collection, fields}` with field names only, `truncated: true` when cut). The event is written in the same transaction as the record (with the SQLite engine above, into the `store_audit_outbox` table), and the audit extension drains it while the host runs; at 1000 undelivered events a write answers `503 audit_backlog` and changes nothing. The store `uses` audit: a collection with `audit: true` refuses activation when audit is not installed or when no principal-providing policy guards its mount, a short-link click is never audited, and turning `audit` off keeps undelivered events in the outbox. The `urlcode-store` ownership commands keep the outbox and add no event. `createStore` returns `{registration, exports, close}`; `AUDIT_BACKLOG` and the `CollectionAuditor` type are exported, and collection write methods take a trailing `actor`.

The `--example` API mount uses `auth: true` when auth is installed, and the `todos` collection declares `audit: true` when audit is installed.

Requests use core's helpers: the body is read before the media type is checked (413 before 415), `Sec-Fetch-Site: cross-site` and duplicated provenance headers are refused, a request with no `Origin` whose `Referer` names a foreign origin is refused, invalid UTF-8 is `invalid_encoding`, and JSON answers carry core's deny-all CSP and referrer policy.

Clearing a field (#738). A `PATCH` body, and the records export's partial `update`, may set an optional field to `null` to remove it from the record; a body of only such clears is a valid change. `null` for a required field is refused with `400 invalid_record` and the field error `is required and cannot be cleared` (and for an increment field, `is an increment field and cannot be cleared`); ownership scoping, `If-Match`/`412` and validation of the other fields apply as before, and a refused patch changes nothing. `PUT` is unchanged: `null` is not a value there. Before this, `null` was refused as the field's wrong type, so no previously accepted request changes meaning. The records export also gains `list(principal, {limit, cursor})`: one page of the principal's scope in creation order, with `total`, `next` and `previous` cursors, `limit` capped at the collection's `pageSize`, the same scoping and `400 invalid_query` as the JSON list.

`urlcode-store reassign --database <file> --project <app> --from <principal id> --to <principal id> [--collection <name>] [--dry-run]` moves every record one principal owns to another (#732). It reads the project to find the `ownership: owner` collections and their `maxRecordsPerOwner`, validates both ids with core's principal pattern, and prints per-collection counts; `--dry-run` writes nothing. When the move would put `--to` over a collection's `maxRecordsPerOwner` the whole operation is refused, naming the collection, and nothing is written. Exported as `reassignOwner`.

Per-owner record limit (#731). An owned collection may declare `maxRecordsPerOwner: N` (at most its `maxRecords`, default 1,000; activation refuses it on a shared collection or above `maxRecords`). A create by a principal that already holds N records answers `409 owner_quota_exceeded`, whose message states no count, limit or collection total; `maxRecords` stays the collection-wide ceiling (`409 collection_full`). Counts are taken from the stored records inside the create's transaction, so they are correct after a restart and after `ownerless-assign`/`ownerless-delete`; records with no owner count toward no principal, and a replayed `Idempotency-Key` answers before anything is counted.

A records export for other extensions (#529): `host()` now returns `StoreExports` (contract version 1), read with `ctx.get('store')` by an extension that requires the store. `records(name)` gives a declared collection's `ownership`, `readOnly` and frozen `fields`, and `create`, `get` and a partial `update` (with optional `ifMatch`) that take the request principal and apply the same ownership scoping, validation, limits and ETags as the JSON API, failing with the same `StoreError` statuses and codes. `createStore` returns the registration and the exports; `storeExtension` is unchanged.

Per-record ownership (#331). A collection may declare `ownership: owner` (default `shared`, unchanged). It is scoped to core's opaque request principal, set by a principal-providing policy on the mount's route (auth's `auth: true`): create stamps the principal as the record's owner, stored beside the record (the database's `owner` column) and never returned; list, read, `PUT`, `PATCH`, `DELETE` and increment see only the caller's records, and another principal's record answers the same `404` as a missing id, before `If-Match` or body checks; a request without a principal is `401 principal_required`; a body naming `_owner` is `400`; `Idempotency-Key` retention is also scoped by principal. Activation refuses an owned collection whose mount has no principal-providing policy, an owned collection with a `key` (and so short links), and a shared collection whose stored records carry an owner. Records written before a collection became owned are served to nobody; the new `urlcode-store ownerless | ownerless-assign --owner <id> | ownerless-delete` commands (and `reportOwnerless`, `assignOwnerless`, `deleteOwnerless`) report them and assign or delete them. The CRUD screen is multi-user-safe only on an owned collection. The `--example` `todos` collection is owned (`ownership: owner`) when auth is installed, in the same command or already; without auth it stays shared and still needs `--ack store:public-write`.

Writes whose `Origin` is one of the operator's site-wide alias origins (`--alias-origin`, `aliasOrigins`) are admitted like the canonical origin, using core's `isSiteOrigin`; an unlisted origin is still refused with `403 forbidden_origin` (#717).

**Default behavior change:** `urlcode extensions add` (and `init --with`) now installs only the capability; the new `--example` flag, the same for every extension, writes the sample behavior it used to write by default (#711). A blank `extensions add store` writes an empty `collections` block, no mount and needs no acknowledgement (`collections` may now be empty); `--example` writes the `todos` collection on `/api/todos` and, with ui, its `/todos` screen, and still requires `--ack store:public-write` without auth. To reproduce the old result, add `--example`.

The store owns its CRUD screen (#709). Screens are declared under `extensions.store.config.screens` (`/todos: {collection: todos, title?, columns?}`, the shape that used to live under `extensions.ui.config.screens`), activation refuses a screen naming an undeclared collection, and the definition's optional `contributes.ui.screens` hands ui a generic description of each, so ui no longer reads `extensions.store`. The scaffold adds the `/todos` screen and its `extension: ui` route when ui is installed. `@jimhoyd/urlcode-ui` is declared an optional peer, and `urlcode.json` records the optional edge as `contributes: ["ui"]`.
