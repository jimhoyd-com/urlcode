# Security boundary

The store is trusted operator code. It runs in the host process, is not sandboxed and is not a multi-tenant boundary. On a shared collection (the default) every caller who can reach a mount can read and (unless `readOnly`) change every record in that collection, so protect mounts with the auth extension or another policy and never put one user's private data in a shared collection another user can reach.

A collection declared `ownership: owner` (#331) scopes every list, read, update, delete and increment to the request's principal, the opaque id core carries from a principal-providing extension's `authorize()` (auth: the verified Better Auth user id); the store never reads a cookie, header or auth table itself. Create stamps the owner, which clients can neither set (a body naming `_owner` is `400`) nor change, and which appears in no response except on a readers mount that declares `showOwner` (below). Another principal's record answers the same `404` as a missing id, checked before `If-Match` and the body, so existence is not confirmed; list totals and cursors cover the caller's records only. A request with no principal is `401` and never falls back to the shared view, and activation refuses an owned collection whose mount route has no principal-providing policy, a `key` on an owned collection (a collection-wide unique key would reveal other owners' values), and a shared collection whose database rows carry an owner. Records written while the collection was shared carry no owner and are served to nobody until the operator assigns or deletes them (`urlcode-store ownerless-assign`/`ownerless-delete`); nothing is auto-assigned. `urlcode-store reassign` (#732) moves every record one principal owns to another; it is an operator action on the database, never reachable through the API, it checks every affected collection's `maxRecordsPerOwner` inside one transaction and refuses the whole move rather than leaving `--to` over its limit, moves every collection or none, and changes nothing but the stored owner and `--from`'s membership entries. These commands open their own connection and may run while the server serves; they need write access to the database file, which is the operator's alone. An owned collection may declare `maxRecordsPerOwner` (#731; at most `maxRecords`, refused on a shared collection): a principal holding that many records gets `409 owner_quota_exceeded` with a fixed message that states no count, limit or collection total, counted in the same database transaction as the create (records with no owner count toward nobody). What ownership does not provide: a guarantee that the collection never fills (`maxRecords` stays collection-wide, enough owners together can reach it, and `409 collection_full` is visible to all; without `maxRecordsPerOwner` one owner can fill it alone), isolation of storage or cost (all owners share one database and its one-writer-at-a-time transactions), manager or support access, or independent security assessment.

The database belongs to the operator: keep it outside the project, on local disk, readable only by the server user. The store creates its directory `0700` and the file `0600` (SQLite gives its `-wal` and `-shm` files the same mode), and refuses a symlinked, hard-linked or group- or other-accessible file. It opens the file with SQLite extensions disabled and `trusted_schema=OFF`, and refuses a file that is not a store database or comes from a newer schema version. Anyone who can write the file can change any record, owner or pending audit event, bypassing every check the store applies; the store re-validates records against the declaration at activation and on every read, not their provenance. Several serving processes on one host, on one release, are supported (#927): each write checks, under the write lock, that the newest activation's declaration and the store schema are its own, and refuses (`503`) otherwise, so a retiring or older process cannot write rows the current declaration forbids. Activation refuses a database directory on a network filesystem (Linux `statfs`; not checked on macOS or Windows) and a live peer on another host (a lease table in the database). A serving process that later finds another host's lease row stops writing: every write checks the lease under its write lock and answers `503` until that host is gone (#978). Liveness is judged by whether a row's heartbeat advances on the observer's own monotonic clock, never by comparing hosts' wall clocks. The lease and the declaration records are rows anyone who can write the file can edit, like every other row: they detect misconfiguration, not an adversary with write access. Protect backups like the data itself.

Requests are bounded (body, record, page and quota limits), validated against the collection's record schema (core's JSON Schema 2020-12 body profile and validator), and JSON-only for writes with core's same-origin rule (`isSameOriginRequest` with `whenAbsent: 'admit'`): a present `Origin` must be the canonical `--origin` or an operator `--alias-origin`, `Sec-Fetch-Site: cross-site` and duplicated provenance headers are refused, and a request with no provenance header at all (a non-browser client) is admitted, because a cross-site browser cannot send a JSON body without a preflight. Behind auth, `auth: true` adds a verified session and refuses a cross-origin write before the store runs. Every stored string is well-formed Unicode (#988): a JSON string or key holding an unpaired UTF-16 surrogate is `400 invalid_unicode` in core's body reader, and `422 invalid_record` through `StoreExports` and host transactions, because SQLite and JavaScript carry such a value as different bytes and `unique`, `intervals`, `key` and list order could not compare it (a bypassed `unique` or `intervals` check then made the next activation refuse the database); activation refuses a stored row holding one. Values are otherwise compared exactly: the store does not normalize Unicode, case or whitespace, so a `unique` handle meant to defeat look-alikes needs a `pattern`. Errors return fixed messages and field names; they never echo submitted values, SQL, SQLite errors or paths. Every value reaches SQLite as a bound parameter, never as SQL text. Passing tests do not establish independent assessment or behavior under crash or disk-full conditions on every filesystem.

A single-record `GET`/`HEAD` returns a strong `ETag`; `PUT`, `PATCH` and `DELETE` honour an `If-Match` header carrying it and refuse with `412` when it no longer matches the record's current state, so a caller can avoid silently clobbering a concurrent writer's change. The check reads the record in the same transaction as the write, and every write moves `updatedAt` (and so the ETag) by at least a millisecond, so of concurrent writers holding one ETag exactly one succeeds. `If-Match` is optional — a write that omits it stays last-write-wins. A short-link mount's declared destination property must be `required` with `format: uri`, and every write to it takes only an absolute HTTP(S) URL without credentials or whitespace; a stored record whose destination is missing or not such a URL (only possible from data written before the short link was declared, since stored rows are judged without `required`) resolves to `404` without counting a click rather than a `302` to it, and `HEAD` never counts a click either way. `Idempotency-Key` retention (#835) is scoped to the request principal, or to the network client when the request has none (hashed together with the header value into one opaque key), so two callers who happen to choose the same key do not collide; an unauthenticated mount has no stronger caller identity than the network client to scope by. The claim, the request fingerprint (method, path, canonical body; hashed) and the result (status and record id, never record values) are recorded in the same transaction as the change. A retry with the same fingerprint replays the first status with the record as it is now, read in the caller's scope (a record since deleted or moved away is `404`); a different request under the same key is `422` and writes nothing.

A declared transition (#835) changes one record from exact property values to constants and store-filled stamps inside one transaction, honouring `If-Match` and `Idempotency-Key`; any refusal writes nothing. A `by: others` transition lets any principal **except** the record's owner act on another principal's record and returns that record (without its owner) to the actor, so it is served only on its own mount, which activation requires to carry a principal-providing policy. Without `members`, whoever that route admits can run the transition on any owned record whose id they know. Properties declared `readOnly: true` in the record schema cannot be set by a body, so the owner cannot write the state a transition guards.

Membership gates (#863) keep permission as application data keyed by the principal id; the store has no roles and auth gains none. A `membership: true` collection holds principal ids under its unique key and has no mount, so no request can add a member or enumerate members; only the operator (`addMember`/`removeMember`, which need write access to the database file) and trusted extension code (`StoreExports`) change it. A transition declaring `members` and a `readers` mount check the caller's membership as the first statement of the request's own transaction, after the principal (`401`) and before any record of the gated collection is read, so a non-member gets one fixed `403 membership_required` for an existing id, a missing id, a malformed id and a list, and learns nothing about which records exist; a removal committed before a request begins applies to it, and a removed member's retried `Idempotency-Key` is refused rather than replayed. Activation refuses a gate naming a collection that is not declared or is not a membership collection, so a typo cannot leave a gate open. A readers mount is read-only (`GET`/`HEAD`; any other method is `405`) and shows members every owner's records; it needs its own route with a principal-providing policy. The operator's `urlcode-store members add|remove|list` (#866) is the command form of `addMember`/`removeMember`/`listMembers`: it needs write access to the database file, validates the principal id and never echoes a refused one. A member's key cannot be changed (an update naming a different key is `422 invalid_record`), so every grant and revocation is a separate change. A membership collection may declare `audit: true`: every added or removed member, from the CLI, the library functions or `StoreExports`, is then recorded as `store.membership.added`/`removed` with the member's principal id as the subject, inserted into the outbox in the same transaction as the member row (refused with `503` at the backlog cap), so an unrecorded grant or revocation never takes effect. The operator path records the actor `operator`, or the principal id the operator passes as `--actor` (#875). That value is operator-asserted, not authenticated: anyone who can run the command against the database can write any id there, so it names who the operator says made the change, and accountability still rests on who holds write access to the database. `urlcode-store reassign` moves a principal's membership with its records in the same transaction, recorded the same way. On an owned collection declaring `audit: true`, `reassign`, `ownerless-assign` and `ownerless-delete` record every record they move or delete (`store.record.reassigned` with the opaque `from`/`to` principal ids in its metadata, or `store.record.deleted`) in the same transaction, and refuse the whole command, before writing, when its events would pass the outbox backlog, so one command changes at most 1000 records of one audited collection. Events the CLI writes reach the audit log only when a server running audit drains the outbox. What it does not provide: an audit trail for a membership collection that does not declare `audit: true`, or for anyone who edits the database file directly.

What a caller may run (#873). List answers carry `may` and single-record answers the `Allow-Transitions` header: the transitions the caller may run on each returned record now. It is computed only from what the caller could already learn, namely the records they were answered, the declaration and their own membership (which a gated transition's `403` would tell them anyway): the caller's membership is looked up once per distinct gate per answer, no other principal's membership is read, and no gate, membership collection or member is named. A caller with no principal is offered only ungated transitions of a shared collection. It is a hint for a client, not an authorization: every transition checks the principal, the gate, the owner and `from` again in its own transaction.

Requester visibility (#866). By default a readers mount never shows the stored owner. With `showOwner: true` on a readers mount every record it answers carries `_owner`, the owner's principal id: an opaque id the principal provider set (for auth, the Better Auth user id; for a bearer key, `apikey:<id>`), never an email, a name or a session. Only members of the declared membership collection receive it, only on that mount; the owner's mount, transition answers and `StoreExports` never include it. The trade-off: a member who can already read every owner's records can now also link them to one account, tell how many requests each account made, and correlate that id with anything else that shows the same id (an auth admin screen, audit events, logs). That is why it is opt-in per collection. If reviewers only need a label, keep it in an ordinary field the owner writes (a display name, a team) instead of turning `showOwner` on; that field is visible to members whether or not `showOwner` is set.

Edit and delete states (#952). `editable` and `deletable` name the states (values of `readOnlyProperties`, so only a declared transition moves a record in or out) in which `PUT`/`PATCH`, an increment (`POST <mount>/<id>/increment/<property>`, #989) and `DELETE` are accepted; in any other the store answers `409 record_locked` with a fixed message and writes nothing, on HTTP, `StoreExports.update` and a host transaction's `update` and `remove`, reading the record under the write lock after the scope and `If-Match` checks, so a request that raced a transition is judged against the committed state. It does not gate creates, transitions, transfers, a short link's click count or the operator's `ownerless-delete`: a transfer still moves a locked record's balance. The `Allow` header and a list's `allow` disclose only the caller's own record's state, which the record already shows. Unique values (#953). `unique` properties are unique across every record, across owners on an owned collection: a create or update that would duplicate one is `409 value_taken`, naming the property and never the value, the other record or its owner. That refusal is an existence oracle: anyone who may create can learn, one request at a time, whether some record holds a value. Declare `unique` only on values meant to be public (a handle a directory shows anyway), never an email or other private identifier, and bound probing with a throttle policy.

Projected readers and gated creates (#929). A readers mount's `properties` narrows it to `id` and the listed properties: it answers nothing else of a record (no `createdAt`, `updatedAt` or unlisted property), refuses a sort or filter on an unlisted property with `400 invalid_query` (an order or a match would disclose it), offers in `may` only transitions whose `from` names listed properties only, and tags records with an `ETag` of the projection, so a change to a hidden property (a transfer's balance) is not observable there. With `properties` the mount may omit `members`; then every principal its route admits (`401` without one) reads the listed properties of every owner's record, which is what a transfer directory needs and exactly what the operator listed. It still discloses the listed values, the number of owned records (`total`), and which ids exist; list only what every signed-in user may know, and add `members` when that is too much. Readers mounts are named (#944) and each keeps its own gate, projection, query rules and `ETag`: a members-gated whole-record mount beside a projected directory shows members everything and everyone else only the listed properties, and activation refuses two readers sharing a mount and any ungated mount without `properties`. `create: {members}` admits only that membership collection's principals to create, checked as the first statement of the write transaction after the principal (`401`, a shared collection included), before the body, the retained `Idempotency-Key` or any record is read, so a non-member learns nothing about the collection's content from a create and a removed member's retry is refused rather than replayed; `StoreExports` and host transactions pass the same gate with the principal they are given. It does not gate reads, updates or deletes: that is ownership, the route's policy, or a `readOnly` collection.

The records export (`StoreExports`, #529), which an extension that requires the store reads with `ctx.get('store')`, is the same collection code without the HTTP layer: the consumer passes the request principal, and ownership scoping, the same `404` for another owner's record, field validation, `maxRecords`, `maxRecordBytes`, `readOnly` and `If-Match`/`412` apply exactly as on the JSON API. The consumer is trusted operator code; passing a principal other than the request's is outside this boundary, and it is responsible for its own request admission (CSRF, origin checks), which the export does not perform. Its `transaction(work)` runs a synchronous callback of that trusted code, unsandboxed and with full Node access, inside one database transaction; it is never offered to route functions or sandboxed code, and it spans only this one database.

A collection with `audit: true` inserts an audit event into the store database's outbox table in the same transaction as each change, so a change and its event persist together or not at all, and refuses writes (503) rather than acting unaudited when 1000 events wait undelivered. Events carry field names, never values. Delivery into audit's own database is a separate step, idempotent on the event id; there is no transaction across the two databases. The store database therefore also holds undelivered audit events until audit drains them; back it up accordingly, before the audit database.

This package follows the [core URLCode security policy](https://github.com/jimhoyd-com/urlcode/security/policy) for reporting. Never post real data or credentials in public issues.
