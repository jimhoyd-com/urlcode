# Security boundary

The store is trusted operator code. It runs in the host process, is not sandboxed and is not a multi-tenant boundary. On a shared collection (the default) every caller who can reach a mount can read and (unless `readOnly`) change every record in that collection, so protect mounts with the auth extension or another policy and never put one user's private data in a shared collection another user can reach.

A collection declared `ownership: owner` (#331) scopes every list, read, update, delete and increment to the request's principal, the opaque id core carries from a principal-providing extension's `authorize()` (auth: the user id, or `apikey:<key id>` for a bearer key); the store never reads a cookie, header or auth table itself. Create stamps the owner, which clients can neither set (a body naming `_owner` is `400`) nor change, and which never appears in a response. Another principal's record answers the same `404` as a missing id, checked before `If-Match` and the body, so existence is not confirmed; list totals and cursors cover the caller's records only. A request with no principal is `401` and never falls back to the shared view, and activation refuses an owned collection whose mount route has no principal-providing policy, a `key` on an owned collection (a collection-wide unique key would reveal other owners' values), and a shared collection whose file holds owned records. Records that predate ownership carry no owner and are served to nobody until the operator assigns or deletes them with the server stopped (`urlcode-store ownerless-assign`/`ownerless-delete`); nothing is auto-assigned. An owned collection may declare `maxRecordsPerOwner` (#731; at most `maxRecords`, refused on a shared collection): a principal holding that many records gets `409 owner_quota_exceeded` with a fixed message that states no count, limit or collection total, checked in the same serialized write as the create, with counts derived from the loaded records (records with no owner count toward nobody). What ownership does not provide: a guarantee that the collection never fills (`maxRecords` stays collection-wide, enough owners together can reach it, and `409 collection_full` is visible to all; without `maxRecordsPerOwner` one owner can fill it alone), isolation of storage or cost (all owners share one file, one lock and one write sequence), manager or support access (auth impersonation acts as the impersonated user), or independent security assessment.

The data directory belongs to the operator: keep it outside the project, on local disk, readable only by the server user. The store creates it `0700` and its files `0600`, takes an exclusive lock and supports one server process per directory. Do not share it over a network filesystem. Protect backups like the data itself.

The directory lock file holds `<pid>:<instance>` (an instance id generated once per process start), written atomically (a uniquely-named temporary file, then linked into place, so no reader can ever see an empty or partial lock file). A lock bearing our own PID but a different instance id is treated as stale and reclaimed rather than as this process already holding it — a container restarted after an unclean exit routinely gets the same PID back (often PID 1), and without this, that restart would refuse to start until an operator removed the lock file by hand. Reclaiming a stale lock first renames it atomically to a unique name and re-reads it there: only a file whose contents still match what was judged stale is removed, so a fresh lock another process claimed in the meantime is linked back and this process refuses to start. Closing the store removes the lock file only while it still carries that store's own `<pid>:<instance>`. This remains a guard against operator mistakes on local disk, not a distributed lock.

Requests are bounded (body, record, page and quota limits), validated against the declared field schema, and JSON-only for writes with a same-origin check on the `Origin` header (the canonical `--origin` or an operator `--alias-origin`, matched by core's `isSiteOrigin`). Errors return fixed messages and field names; they never echo submitted values, file contents or paths. Passing tests do not establish independent assessment or behavior under crash or disk-full conditions on every filesystem.

A single-record `GET`/`HEAD` returns a strong `ETag`; `PUT`, `PATCH` and `DELETE` honour an `If-Match` header carrying it and refuse with `412` when it no longer matches the record's current state, so a caller can avoid silently clobbering a concurrent writer's change. `If-Match` is optional — a write that omits it stays last-write-wins, unchanged from before. A short-link mount's declared destination field must be `required`; a record without it (only possible from data written before that requirement existed) resolves to `404` without counting a click rather than a `302` to `Location: undefined`, and `HEAD` never counts a click either way. `Idempotency-Key` retention is scoped per network client (hashed together with the header value into one opaque key), so two callers who happen to choose the same key do not collide; an unauthenticated mount has no stronger caller identity than the network client to scope by.

This package follows the [core URLCode security policy](../../SECURITY.md) for reporting. Never post real data or credentials in public issues.
