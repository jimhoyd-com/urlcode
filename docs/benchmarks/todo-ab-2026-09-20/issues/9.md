**Tried:** find every built-in capability relevant to a JSON API app before writing code.
**Expected:** `llms.txt`/`docs/AI-AUTHORING.md` route "I need X" to the feature.
**Got:** the built-in security-headers policy is documented only in `docs/POLICIES.md`/`HTTP.md`; it is absent from `llms.txt` and `AI-AUTHORING.md`. Run 1 shipped an app with no security headers and never discovered it (run 2 used the policy and got a CSP header). This is a discoverability failure of an existing capability. Also, `static.cacheControl` is a four-value enum that is visible only in the schema or via a validation error (run 2), and `recipes search` for CRUD/persistence returns nothing.
**Suggestion:** a compact task -> feature index in `llms.txt` (security headers, cache control, body limits, method gating, ...) and `urlcode context` output; document the `cacheControl` values in `docs/yaml/assets.md`.
**Evidence:** an A/B benchmark on URLCode 0.4.1 with Sonnet 5 agents building the same Todo app from the repo docs. Run 1 (benchmark Agent B, no authoring skill, no browser check) and run 2 (session "Todo application with URLCode", authoring skill loaded, tightened prompt) hit this independently. n=1 each; single small app, so treat frequency as anecdotal. The Agent A control (no URLCode) needed 2 shell calls and 0 dependencies for the same app.
**Not verified:** whether run 2 found the policy through the authoring skill or `urlcode context`.
