# Release operations

Core and every add-on (the extensions under `packages/` and the artifacts under
`artifacts/`) share one version. A release is a merged pull request that
contains only a version change; the push to `main` releases it. Two workflows
do the work: **Release pull request** (`release.yml`) keeps that pull request
open with [release-please](https://github.com/googleapis/release-please), and
**Publish release** (`publish.yml`) ships whatever version reaches `main`. The
[release security](RELEASE-SECURITY.md) page explains what the pipeline
guarantees and [package and channel alignment](VERSION-ALIGNMENT.md) lists the
channels. A published release is not a production-readiness claim; see
[production readiness](#production-readiness) below.

## Release a version

1. After every **Publish release** run on `main` (or when dispatched),
   **Release pull request** runs release-please's `release-pr` command (its npm
   CLI, pinned with its dependencies by `.github/release-please/package-lock.json`)
   with `release-please-config.json`. It reads the
   [conventional commits](https://www.conventionalcommits.org/) merged since
   the last `v*` release and opens or updates one pull request, titled
   `chore(main): release X.Y.Z`, that moves every version declaration it is
   configured for: `package.json`, `package-lock.json`'s root entry,
   `.release-please-manifest.json`, each add-on's version and exact peers on
   core and its siblings, the exact `@jimhoyd/urlcode` dependency of every
   `examples/*/package.json` that declares one, core's `CORE_VERSION` literal
   (`packages/core/src/release.ts`, which the CLI version, the MCP `serverInfo`
   and every installed docs link read), the Claude plugin and marketplace
   manifests, and every marked version block and line in the Markdown and
   `llms.txt` ([current-version references](DEVELOPMENT-PIPELINE.md#current-version-references-in-documentation)). The same
   job then runs, on that pull request's branch, what release-please cannot
   do: `npm install --package-lock-only --ignore-scripts` for the add-ons'
   lockfile entries, and `node scripts/release-versions.ts sync`, which moves
   the pinned links in non-Markdown text (schema descriptions, example and
   starter YAML, the starter's schema URL and Action ref) and regenerates
   `llms-full.txt`, whose links name the release tag. It commits the result to
   the pull request.

   The version follows the commits: while the version is below 1.0.0, a `feat`
   or `fix` moves the patch version and a breaking change the minor version.
   To choose it, add a `Release-As: X.Y.Z` (or `X.Y.Z-alpha.N`) footer to a
   commit on `main`. `node scripts/release-versions.ts check`, part of
   `npm run check`, fails CI whenever any declaration drifts, a Markdown line
   release-please would corrupt sits in a version block, or
   `release-please-config.json` misses an add-on or example.
2. Review the release pull request and merge it once the required checks pass.
   Release notes are generated by GitHub from the titles of the pull requests
   merged since the previous release, so write feature pull request titles for
   readers.
3. Watch **Publish release** (`.github/workflows/publish.yml`) on the merge
   commit. When it has released, the next **Release pull request** run labels
   the merged pull request `autorelease: tagged`; release-please opens no new
   pull request while a merged one is still `autorelease: pending`.

| Job | What it does |
| --- | --- |
| `plan` | Reads the version; releases only when the `v<version>` GitHub Release or the npm version is missing |
| `ci` | Runs `ci.yml` on the commit; a release run gets the complete OS × Node matrix and the cross-workspace integration |
| `build` | Builds core and every add-on, runs `release:pack`, attests every file and uploads them as the run's artifact |
| `publish` | In the `release` environment: 1. GitHub Release (creates the tag), 2. public add-on URLs checked against core's pins, 3. core to npm, 4. Homebrew formula (stable), 5. GHCR image |
| `verify` | A fresh site from the public channels (`npx … init`, every add-on, `list --strict`, `validate`) and `install.sh`; opens a `release`-labelled issue on failure |

A push to `main` that does not change the version runs `plan` and `ci` only.

## When a run fails

- **Before `publish`** (`ci` or `build`): nothing is public. Fix it in a pull
  request; the next push to `main` plans the same unreleased version again.
- **In `publish`**: use **Re-run failed jobs**. The re-run reuses the files the
  `build` job attested, and every step is idempotent: an existing GitHub
  Release asset must be byte-identical and is never replaced, a missing one is
  uploaded, npm skips a version already published with identical bytes and
  refuses different bytes, and Homebrew and GHCR skip what is already there.
  When the original run can no longer be re-run, dispatch **Publish release** from
  `main`: it rebuilds from the dispatched commit and completes the release only
  when the rebuilt files match what is already published.
- **In `verify`**: the release is public and stays public. The job opens a
  `release` issue. Fix forward with the next version and deprecate the bad one:
  `npm deprecate @jimhoyd/urlcode@X.Y.Z "Use X.Y.Z+1: <reason>"`.
- **In `template`**: re-run the job, or run
  `npm run release:template -- --version X.Y.Z --execute` locally. It opens,
  and never merges, the template pull request.

Never delete, move or recreate a `v*` tag or a release asset; the tag rulesets
and immutable releases refuse it, and a published version is fixed only by a
newer one.

## Inspect locally

```sh
npm run build && npm run build:addons
npm run release:pack -- --out /tmp/release   # every tarball, addons.json, SBOM, triage, formula, SHA256SUMS
npm run ci:build-fidelity                    # two clean builds must pack identical tarballs and pins
```

`release:pack` writes the release pins into `dist/addons.json`; run
`npm run build` afterwards to restore the development manifest.

## One-time repository settings

- **Tag ruleset** (`.github/rulesets/release-tags.json`): nobody may update or
  delete a `v*` tag. Creation is not restricted by a ruleset (GitHub Actions
  cannot be a bypass actor on a user-owned repository); the `publish` job
  creates the tag with `gh release create`, running in the `release`
  environment limited to `main`. The only other job with `contents: write` is
  `release.yml`'s, which pushes the release pull request's branch and never
  tags (`skip-github-release`).
- **Immutable releases** enabled for the repository, so a published release's
  tag and assets cannot change.
- **`release` environment**: deployment branches limited to `main`, no required
  reviewers (merging the bump is the approval). Its secret
  `HOMEBREW_TAP_TOKEN` can push to `jimhoyd-com/homebrew-urlcode`.
- **npm trusted publisher** for `@jimhoyd/urlcode`: repository
  `jimhoyd-com/urlcode`, workflow `publish.yml`, environment `release`. Renaming
  the workflow breaks publishing.
- The **`release` label** exists (`.github/labels.json`). release-please adds
  its own `autorelease: pending` and `autorelease: tagged` labels, which
  GitHub creates on first use.
- **`RELEASE_PLEASE_TOKEN`** repository secret: a fine-grained token (or GitHub
  App token) for this repository with contents and pull requests read and
  write. A pull request opened or pushed with the workflow's own
  `GITHUB_TOKEN` starts no workflow, so without this secret `release.yml`
  still maintains the release pull request, but its required checks do not
  start until someone closes and reopens it.

## Production readiness

A published release means the packages were published. It does **not**
establish production readiness, independent security assessment, hostile
multi-tenant isolation or support commitments. This is the one authoritative
production-gate list; other guides link here instead of repeating it.

### Evidence in the repository

- `npm run verify` checks lint, types, generated references and unit and
  real-HTTP behavior. `npm run test:package` exercises the packed archive and
  starter. A passing check covers only its tested behavior.
- Native routes do not execute project code unless middleware is attached.
  Functions and middleware are trusted Node code by default; `sandbox: true`
  opts into the bounded QuickJS/WASM path. Binding injection is externally
  granted and revision-pinned in either mode. The portable contract is defined
  by the [specification](SPECIFICATION.md) and [capabilities](CAPABILITIES.md).
- `node scripts/operational-drills.ts` creates and deletes its own temporary
  project, sends mixed real HTTP requests to native redirects and `function`
  routes, rejects a bad reload, and activates and rolls back a configuration.
  `URLCODE_SOAK_SECONDS=60` selects a longer run (1–3600 seconds, default 5).
  Output is JSON with request count, batch p99 duration and RSS; batch latency
  is not per-request p99 or a capacity promise. CI runs the short drill on
  every leg of the complete 3-OS × 3-Node matrix for a release run, the merge
  queue, a dispatch and the nightly sweep; pull requests and other pushes run
  it on Linux with Node 24.
- Core has no durable store, so the drill has no backup/restore or
  disk-exhaustion exercise. Extensions owning durable state own that proof:
  `auth` ([auth](../packages/auth/README.md#add-it)) and `store` ([store](STORE.md)).

### Gates before production approval

The deployment owner records the workload, exact revisions, environment,
commands, results and an accountable owner for each open gate:

1. Independent review of the host and `sandbox: true` boundaries
   ([sandbox review](SANDBOX-REVIEW.md)).
2. Sustained load and soak through the real TLS/ingress path, with workload SLOs,
   tail latency, rejection/error rate, RSS and recovery evidence.
3. Kill/restart, resource-exhaustion and deployment/rollback exercises using the
   chosen supervisor and ingress. Durable-state extensions own their own
   backup/restore proof.
4. Tested alerting and ownership for errors, latency, readiness, logs, disk and
   restart failures.
5. Any support, publication or provider commitments the deployment needs.

Local and CI passes do not close these gates. `urlcode verify-deployment --target`
([deployment checks](DEPLOYMENT-CHECKS.md)) records that the deployed responses
match the project and is the first step of the rollback exercise, not a
substitute for it.

| Exercise | Acceptance evidence |
|---|---|
| Soak | At least 24 hours at expected peak and burst load through actual TLS/ingress; native/function mix, slow clients, response correctness, p50/p95/p99, throughput, error/rejection rate, RSS plateau, CPU and FD growth. Define numerical SLOs before starting |
| Kill/restart | Kill the server with outstanding requests. Reconcile uncertain mutations by request ID, restore readiness, and prove no duplicate side effects from application code |
| Rollback | Deploy the new build by exact digest beside last-good, run route assertions, switch ingress, drain, then switch back. Verify configuration/policy compatibility |
| Monitoring | Deliver test alerts for missing logs, sustained errors, pool rejection/failure, low disk, restart storms and failed readiness to a named on-call owner |

A deployment that adds a durable-state extension adds that extension's
backup/restore, logical export/import and disk/log exhaustion exercises.
Record date, operator, source/app/policy/image digests, topology,
hardware/limits, commands, duration, dataset size, raw metrics/log locations,
result and unresolved findings. A reviewer signs the acceptance record; a blank
record is not a pass.
